# 야구 투구 영상 검수

자동 공 추적기가 먼저 위치 후보와 분리 후보 구간을 제시하고, 사람이 원본 프레임에서 확인하는 도구다. 서버가 영상 프레임을 불러오고 검수할 때마다 작업자별 JSON을 저장한다. ZIP을 주고받을 필요가 없다.

## 작업자

1. 공통 사이트 주소를 연다. 본인의 작업자 번호를 고르고 공통 접속 코드를 처음 한 번 입력한다. 이후 같은 브라우저에서는 작업자를 기억한다. 내 씬 목록에서 진행률과 확인이 필요한 씬을 확인한다.
2. 먼저 **손에 있음 / 날아가는 중 / 잡힌 상태 / 구분 안 됨** 중 하나를 고른다. 공이 보이더라도 손에 쥐고 있으면 손에 있음이다. 손끝과 공이 흐리게 겹쳐 분리를 알 수 없으면 구분 안 됨으로 남긴다. 손이나 글러브에 있는 공은 중심점을 찍지 않는다.
3. **날아가는 중**을 고른 경우에만 위치 입력을 연다. 노란 후보가 공 중심이면 **이 위치가 맞음(1)**, 틀리면 **위치 수정(2)** 후 중심점을 클릭한다. 후보가 없으면 중심점을 직접 클릭한다. 상태나 위치를 저장하면 다음 미확인 프레임으로 넘어간다. 구분 안 됨은 **3**이다. 검출 실패를 공 없음으로 자동 처리하지 않는다.
4. 릴리스 앞뒤 사진을 보고 **맞음 / 다른 시점 / 안 보임**으로 답한다. 직접 지정한 접촉·분리 값이 있으면 그 프레임 사진을 표시하며, 없을 때만 자동 후보를 표시한다. 사진을 누르면 해당 프레임을 크게 볼 수 있다. 다른 시점이면 상세 영역에서 마지막 확실한 접촉과 첫 확실한 분리를 지정한다. 입력값은 미검증 관찰이며, 가림이나 흐림으로 접촉을 확정하지 못하면 릴리스 판독 불가로 남긴다.
5. 한 씬의 모든 프레임을 표시하면 **이 씬 제출**을 누른다. 다른 씬을 끝내지 않아도 제출할 수 있다. 릴리스와 충돌하는 표시가 있으면 원래 판독을 보존해 **접수 완료 · 검토 필요**로 전달한다. 접수 뒤 다음 씬으로 넘어간다. 좌우 방향키로 이전 판독을 다시 확인하고 수정할 수 있으며, 수정한 씬은 다시 제출한다.

흰 원은 사람이 확인한 위치다. 후보를 보기만 하거나 틀림만 누른 상태는 판독 완료로 처리하지 않는다. 씬 접수는 검증 통과와 다르다. 불일치가 있는 접수에는 검토 사유와 프레임을 남기며 연구용 결과는 만들지 않는다. **전체 결과 내보내기**의 JSON과 전체 입력 검사 결과 제출은 기존처럼 모든 씬의 릴리스 일관성 검사까지 통과해야 가능하다. 파일 기반 오프라인 작업도 유지한다.

새 판독은 `held`(손에 있음), `caught`(잡힘), `ball`(날아가는 공 중심), `unknown`(판독 불가)을 구분한다. 기존 `absent` 기록은 손과 글러브 중 어느 상태인지 추측해 변환하지 않는다. 기존 추적기용 내보내기의 `negative`는 **자유 비행 공이 없는 프레임**이므로 `held`, `caught`, `absent`를 포함한다. 물리적으로 공이 존재하지 않는다는 뜻이 아니다. 구체적 상태는 `human_review.marks`에 그대로 남는다. 손·글러브 상태에는 좌표를 저장하지 않고, 기존 사용자 판독과 접수 사본은 자동 수정하지 않는다.

## 자동 후보 생성

기존 `experiments/shared_ball_tracking/study.py`의 RGB·움직임 후보와 앱 추적기의 `proposal_union`을 사용한다. `tracker-root`는 해당 코드가 있는 로컬 checkout이다. 현재 작업은 선행 추적기 브랜치의 모델을 재학습하거나 성능 기준으로 다시 선택하지 않는다.

    python tools/pitch_labeler/suggest.py batch-folder/assignment.json assisted-spec.json tracker-root batch-folder/assignment-assisted-v1.json

`assisted-spec.json`은 아래 작업 배정 목록에 각 영상의 원본 픽셀 `anchors:[[x1,y1],[x2,y2]]`를 추가한다. 이 영역은 운영자가 투수에서 포수로 향하는 장면을 보고 지정한 검색 범위이며 자동 검출 결과나 실측 구속이 아니다. 원본 SHA-256 일치 후 실제 RGB 프레임을 처리하며, 좌표는 원본 해상도로 되돌린다. 원래 배정 파일과 이전 후보 파일을 덮어쓰지 않는다.

`assistance.points`에는 관측 후보만 넣는다. 보간점이나 검출되지 않은 프레임의 음성 라벨은 생성하지 않는다. `release_hint`는 3개 연속 검출의 시작 직전/시작 프레임으로 만든 **검색 제안**이며 실제 손 접촉 판정이 아니다. 사람이 별도로 확인한다. 후보를 승인해도 다른 미판독 프레임을 자동 완성하지 않는다.

모델 후보, 사용한 추적기 커밋·입력 목록 해시, 사람의 승인·수정·거절·판독 불가를 별도로 저장한다. 과거 수동 판독의 좌표를 후보로 대체하지 않는다. 이 자료는 `machine_assisted`이며 독립 블라인드 정답이나 모델 정확도 검증으로 취급하지 않는다. `compare.py`도 이를 명시한다. 두 작업자의 불일치 검토와 개발용 수정 자료 수집에는 사용할 수 있다.

## 작업 배정과 검산

Python 환경에 OpenCV가 필요하다. 원본 파일 경로, 작업 ID, 자료 유형, 원본 프레임의 시작·끝 번호를 지정한 목록으로 작업 폴더를 만든다.

    python tools/pitch_labeler/prepare.py private-spec.json batch-folder
    node --test tools/pitch_labeler/*.test.cjs
    python -m unittest discover -s tools/pitch_labeler -p "test_*.py"
    python tools/pitch_labeler/compare.py batch-folder/assignment.json reader-a.json reader-b.json review.json

배정 목록 형식은 다음과 같다.

    {"batch":"sample-a","clips":[{"id":"pitch-01","group":"MLB","path":"pitch.mp4","window":[100,130]}]}

작업 폴더의 PNG는 OpenCV로 원본 영상을 순서대로 디코드한 뒤 크기를 바꾸지 않고 저장한다. 번호는 0부터 시작하는 원본 디코드 인덱스다. 제출값은 원본 픽셀 좌표와 영상 SHA-256을 보존한다. 'release'는 기존 연구 코드의 정의에 따라 [마지막 확실한 접촉, 첫 확실한 분리 - 1]이며, 관찰한 두 프레임 번호는 별도로 남긴다. 범위를 알 수 없으면 null로 남긴다.

두 사람의 결과를 대조하면 상태가 다른 프레임, 각각의 릴리스 범위, 공 중심 간 거리(가로 960px 환산)가 나온다. 의견이 다른 프레임은 원본으로 돌아가 확인한다. 비교 보고서는 두 관찰을 자동 합치지 않는다. 기존 연구 실행에 연결할 때는 의뢰자가 영상 경로와 탐색 영역을 별도로 지정하고, 릴리스 범위가 없는 항목은 시간 기반 검증에서 제외 사유를 기록한다.

연습 화면은 합성 프레임이며 연구 결과로 제출할 수 없다. 원본 영상 및 실제 작업 폴더는 연구 저장소와 사이트 배포물에서 분리한다. 화면 설계에는 [unslop](https://heydamir.design/unslop), Damir Sokolovsky, CC BY 4.0 지침을 적용했다.

## 로컬 서버 자동 저장

    node tools/pitch_labeler/serve.cjs batch-folder/assignment-assisted-v1.json readers.json records 8767 portal.json

서버는 127.0.0.1에서 실행한다. 외부 HTTPS 터널은 이 포트만 연결한다. `readers.json`은 작업자별 내부 키를 보존하고, `portal.json`에는 12자 이상 난수 `accessCode`를 둔다. 두 파일은 공개 경로와 Git 밖에 둔다. 작업자에게는 모두 같은 사이트 주소와 공통 접속 코드를 전달한다. 화면에서 R01/R02를 고르면 기존 판독을 이어서 불러온다.

공통 접속 코드는 팀 진입용이다. 이를 아는 사람은 작업자 번호를 바꿀 수 있으므로 번호는 기록을 구분하는 용도이며 개인별 접근 통제를 뜻하지 않는다. 인증 전에는 프레임과 판독 JSON을 제공하지 않는다. 접속 시도는 분당 20회로 제한한다. 입력한 코드는 URL에 넣지 않으며, 성공한 작업자 키는 브라우저에 기억한다. 저장 대기·실패·충돌 중에는 작업자 전환을 막는다. 기존 키 링크도 읽을 수 있고 로그인 성공 후 주소에서 키를 제거해 공통 주소로 정리한다.

판독을 변경할 때마다 서버가 작업자별 JSON 파일에 저장한다. 같은 링크로 다시 들어오면 저장한 판독을 이어서 할 수 있다. 연결에 실패하면 브라우저가 미전송 내용을 보관하고 다시 저장 버튼을 표시한다. 다른 탭에서 더 최근에 저장한 기록은 자동으로 덮어쓰지 않는다. 제출 후 내용을 수정하면 다시 제출해야 한다.

관리자는 `records`의 작업자별 JSON을 확인할 수 있다. 씬 제출은 `sceneSubmissions`에 최신 접수, `sceneSubmissionHistory`에 접수 이력을 저장한다. 접수에는 원본 영상 해시, 판독 사본과 해시, 접수 시각, 입력 검사 결과와 검토 대상 프레임이 포함된다. `validation: needs_review`이면 해당 접수의 `result`는 null이다. 입력 검사 통과는 판독 정확도나 연구 검증 통과를 뜻하지 않는다.

씬별 접수는 전체 작업의 `submittedAt`이나 `result`를 채우지 않는다. 전체 입력 검사 결과 제출을 마친 파일만 기존 `compare.py`에 바로 넘긴다. 저장 중 제출을 눌러도 선행 자동 저장이 끝난 뒤 같은 순서로 제출하고 서버 응답을 기다린다. 전송 실패 시 제출 요청도 브라우저에 보관해 다시 저장으로 재시도한다. 접수 후 판독을 바꾸면 기존 접수 사본은 유지하고 화면에는 다시 제출이 필요하다고 표시한다.

작업자 키와 판독 파일은 서버 공개 경로와 분리한다. 프레임 API는 유효한 작업자 키로 배정 목록에 있는 PNG만 제공한다.
